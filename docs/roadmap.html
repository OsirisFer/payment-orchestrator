Fase 1
payment-core — scaffold generado
Generamos el primer servicio: va a ser el corazón del sistema, el que registra cada pago y decide si se aprueba o se rechaza. Para eso le dimos la capacidad de hablar por HTTP (web) y de guardar datos en una base relacional (data-jpa + postgresql) — lo que nos lleva directo al siguiente paso: necesita una base de datos donde guardar algo.
Conceptos vistos
Maven / pom.xml: administra las dependencias (librerías externas) y cómo se compila el proyecto — equivalente a package.json en Node.
mvnw (Maven Wrapper): script que corre Maven con la versión correcta sin instalarlo aparte en tu máquina.
@SpringBootApplication: anotación "maestra" que le dice a Spring dónde arrancar y qué paquete escanear para armar la app automáticamente.
SpringApplication.run(...): la línea que efectivamente prende el servidor web embebido y deja la app escuchando pedidos HTTP.
Dependencia web: habilita exponer endpoints REST.
Dependencia data-jpa: da JPA/Hibernate, para guardar objetos Java en una base relacional sin escribir SQL a mano.
Dependencia postgresql: el driver/traductor para que Java hable con Postgres específicamente.
Dependencia validation: valida datos de entrada de forma declarativa (ej: monto no negativo).
Dependencia devtools: reinicia la app sola cada vez que guardás un cambio.
application.properties: archivo de configuración (puerto, conexión a base de datos, etc.), todavía vacío.

Fase 1
docker-compose.yml creado
payment-core iba a necesitar esa base de datos, pero en vez de instalar Postgres directo en tu máquina, armamos la receta para levantarlo aislado en un contenedor — lista para usar, pero todavía apagada.
Conceptos vistos
Docker / contenedor: empaqueta un programa (Postgres) con todo lo que necesita para correr, aislado del resto de tu máquina.
docker-compose: levanta varios contenedores juntos con un solo archivo y un solo comando.
image: postgres:16: la "plantilla" oficial que Docker descarga y usa para crear el contenedor.
environment: variables que Postgres lee al arrancar por primera vez para crear base, usuario y contraseña solo.
ports "5432:5432": conecta el puerto de adentro del contenedor con el puerto de tu máquina, para que payment-core (que corre afuera del contenedor) se pueda conectar.
volumes: guarda los datos fuera del contenedor, para no perderlos si lo recreás.
✓
Fase 1
Docker Desktop levantado y Postgres corriendo
Prendimos esa base de datos de verdad. Ahora hay un Postgres real escuchando en el puerto 5432, esperando a que payment-core se conecte — eso todavía falta configurarlo, pero ya está la pieza lista.
Conceptos vistos
Docker Desktop vs CLI docker: Docker Desktop es la app con interfaz gráfica que levanta el motor (daemon) que el comando docker necesita para funcionar.
PATH del sistema: para que el comando docker funcione en cualquier terminal, su ubicación tiene que estar en la variable PATH — lo agregamos a ~/.zshrc.
docker compose up -d: descarga la imagen si falta y levanta los contenedores en segundo plano (-d = detached).

Fase 1
reconciliation-worker — scaffold
Una vez que payment-core y webhook-listener se estén hablando, va a hacer falta alguien que de tanto en tanto revise que las cuentas cierren — este servicio va a comparar lo que payment-core anotó contra lo que dicen de verdad los proveedores.
Vamos a ver
Scheduled jobs en Spring (@Scheduled) — tareas que corren solas cada cierto tiempo.
6
Fase 1
mcp-agent-gateway — scaffold
El cuarto y último servicio del esqueleto: una puerta de entrada especial para que un agente de IA pueda pedir un pago en nuestro nombre, en vez de un humano llamando a la API REST.
Vamos a ver
Qué es un servidor MCP y cómo un agente de IA lo usa para "llamar" a una función tuya.
7
Fase 2
Entidad Payment + máquina de estados
Con los 4 servicios ya armados, volvemos a payment-core para darle su primera funcionalidad real: una clase Payment que Hibernate va a convertir sola en una fila de la tabla de ese Postgres que ya tenemos corriendo, controlada por una máquina de estados.
Vamos a ver
@Entity, @Id, @Enumerated — cómo una clase Java se convierte en una tabla de base de datos.
Qué es una máquina de estados y por qué importa tanto en pagos (PENDING → APPROVED/REJECTED).
8
Fase 2
Idempotencia con Redis
Una vez que Payment ya pueda guardarse, hay que blindarlo: si una misma solicitud llega dos veces (por un reintento de red), Redis va a guardar una "marca" para que la segunda vez no se cobre de nuevo.
Vamos a ver
Qué es Redis (cache en memoria) y cómo usamos un TTL (tiempo de vida) para una idempotency key.

Fase 3
Integración sandbox Stripe + Mercado Pago
Con el core ya sólido y protegido, lo conectamos por primera vez con el mundo real: cuentas de prueba de Stripe y Mercado Pago, para ver un pago de verdad (con plata falsa) recorriendo todo el camino que armamos.
Vamos a ver
Qué es un ambiente sandbox/test de un proveedor de pagos, y cómo normalizar respuestas distintas a un formato propio.
